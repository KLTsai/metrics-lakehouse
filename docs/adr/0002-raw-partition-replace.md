# raw 層原樣入倉;重跑時整個分區換新,不在入倉時去重

入倉層(T1.4)把客戶檔案原封不動搬進倉庫,重複列、空值、寫法怪的值全部照收。同一天的資料要重新入倉時,先把那一天那個租戶的舊資料整塊刪掉,再把檔案整份插回去。我們沒有採用「入倉時順手去重」的做法(資料庫術語叫 upsert:主鍵已存在就更新,不存在就插入)。

## raw 層長什麼樣

- `metrics` 資料庫開一個 `raw` schema,每張上傳表對應一張表:`raw.transaction_detail`、`raw.accounts_receivable`。
- 資料欄全部是 `text`,不轉型。欄名用契約層的英文名;中文表頭由 loader 照契約對照表換成英文。
- 每列多四個入倉層自己填的欄位:`tenant_id`(租戶)、`file_date`(檔案日)、`source_filename`(來源檔名)、`loaded_at`(入倉時間)。
- 上游檔案裡有什麼就存什麼。重複列不去掉,空值不補,寫法怪的值不改。清洗是 dbt(L3)的事。

## 先講三個詞

**分區**:倉庫刪補的最小單位,等於「一個租戶的一個檔案日」。alpha 的 2026-01-01 是一個分區,beta 的 2026-01-01 是另一個。一個分區裡有兩張表(訂單、應收帳款),loader 對它們分別處理。

**重跑要安全**:同一天的入倉不管跑幾次,倉庫裡的結果都跟只跑一次一樣。中途當掉再跑、隔天補跑、手動重跑,都不能讓資料變多或變少。業界叫 idempotency。

**分區替換**:達成「重跑安全」的手段。每次入倉都做同一件事:刪掉整個分區,再把檔案整份插入。兩步包在同一個資料庫交易裡,所以要嘛全做完,要嘛一件都不算做過。

## Before:如果入倉時就去重,會發生什麼

直覺的做法是入倉時用 upsert:遇到主鍵已存在的列就覆蓋,沒有就插入。這樣重跑也安全,而且順手把重複列處理掉了。我們拒絕它,因為它會造成三件具體的事。

**第一件:品質層的測試永遠抓不到東西。** T2.4 的驗證標準是「產生器注入的每一類髒資料都被至少一個 test 抓到」。產生器對每個租戶的每張表整體注入 5% 的重複列(以該表的基底列數為分母),再隨機分佈到各檔案日,所以單日的比例會浮動。這些重複列就是要讓 dbt 的 `unique` test 有東西抓。如果入倉時就把重複列吃掉,`unique` test 每次都綠,不是因為資料乾淨,是因為證據在它看到之前就被銷毀了。品質層拿不出任何戰績。

**第二件:錯的主鍵會被安靜地吞掉。** upsert 靠主鍵判斷「這列是不是已經有了」,所以它假設主鍵可信。但 raw 層的前提正好相反:上游是客戶手上的檔案,什麼都可能發生。主鍵一旦出問題,upsert 不會報錯,只會做錯事:

- 兩列主鍵都是空的,upsert 會把它們當成同一列,後面那列覆蓋前面那列。幾列變一列,沒有任何紀錄。
- 主鍵多了一個空格或大小寫不同,upsert 會把它當成一列新資料插進去。真正的重複被放過了。
- 兩列不同的資料被上游誤填同一個主鍵,後到的那列直接蓋掉先到的。資料少了一列,沒有人知道。

這跟藍本產品那次「欄位被 silently drop、幾個月沒人發現」的事故是同一種形狀:系統沒有壞,只是安靜地把資料弄丟。產生器目前刻意不對主鍵注入缺值(ADR 0001),但入倉層不能建立在「主鍵一定乾淨」的假設上。

**第三件:「重跑」和「補跑」變成兩套邏輯。** upsert 只會覆蓋和插入,不會刪除。上游重送一份檔案、裡面少了幾列,upsert 之後那幾列還留在倉庫裡。要處理這種情況,就得另外寫一套「先找出哪些列該刪」的邏輯。T1.5 的 backfill(刪掉某一天再補回來)也得各自處理刪與補。分區替換沒有這個問題:刪與補是同一個動作。

## After:分區替換實際怎麼運作

loader(`ingestion/raw_loader.py`)對每個分區做的事是:開一個交易,`DELETE` 這個分區的所有列,把檔案裡的每一列 `INSERT` 進去,結束交易。中間任何一步出錯,交易回滾,倉庫回到入倉前的樣子。

這個設計在 T1.4 和 T1.5 用真實容器驗過:

- 同一天連跑三次,資料指紋(排除 `loaded_at`)完全一致。重跑沒有讓資料變多。
- 在 `DELETE` 之後、`INSERT` 之前把程序殺掉(SIGKILL),倉庫零殘留,舊資料還在;再跑一次等於乾淨跑一次。
- 刪掉 2026-01-02 兩張表的分區,用 Airflow 的 backfill 補回,各表總數(1050 / 1050)與刪除前的快照完全一致,`DagRun` 沒有重複。
- 遲到列跟著它所在的檔案走:歸屬 1/1、實際出現在 1/3 檔案的 3 列,backfill 1/1 之後仍留在 01-03 分區,各只有一份。補 1/1 只動 1/1 那個分區,不會牽扯到別天。

## 已知邊界

交易的單位比分區更細:loader 對「一個租戶、一張表、一個檔案日」開一個交易,所以一天兩個租戶各兩張表,總共是四個交易,不是一個。程序如果剛好死在兩個交易之間,會短暫出現「alpha 的訂單已入倉、alpha 的應收帳款還沒」這種不對稱狀態。重跑一次就全部換新,不需要人工清理。這是接受的取捨,沒有為它加一個包住整天的大交易。
