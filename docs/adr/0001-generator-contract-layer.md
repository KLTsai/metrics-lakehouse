# 產生器對上傳契約層出資料,兩張表,注入精確可驗

T0.5 合成資料產生器(`generator/`)只生成藍本**上傳契約層**的原始欄位(客戶上傳檔的長相,中文表頭),不生成落地層衍生欄位(未收金額、逾期天數、調整後金額等)——衍生欄位是 L3(dbt marts,T2.3)的責任。這條線劃錯,Phase 2 會變成「產生器已算好、dbt 沒事做」,建模戰績落空。

表只有兩張:訂單 `transaction_detail`(16 欄,CRO/業務側)與應收帳款 `accounts_receivable`(13 欄,CFO/財務側),兩表共享客戶軸(`客戶編號` ↔ `客戶代碼`),構成「銷售 → 開發票 → 收款」一條可建模的敘事。schema 逐欄照抄藍本 `target_tables/{cro,cfo}.py`,不自行增刪欄位。

## 否決的選項

- **客戶主檔**:藍本八張表皆無客戶主檔(客戶資料散在 AR 與訂單),憑空捏表違反「schema 取自真實產品」原則(PLAN 決策 #4)。改為將訂單表 `客戶編號`(非 required)納入缺值注入欄位池;孤兒鍵留作未來開關(2026-08-13 裁示,不加第五類髒資料)。
- **應付帳款**:結構上是 AR 的逐欄鏡像(供應商↔客戶、已付↔已收、同款 default_rule),對髒資料與 pipeline 練習零新機制;且採購側交易表不在 scope,AP 會是無 join 對象的孤島表。觸發點:Phase 2 選指標若要講 CCC(現金轉換循環)類故事,再開 v2 並先改 PLAN。

## 注入設計:為了精確斷言而互斥

驗證標準是**精確相等**(注入筆數 = `floor(分母 × rate)`),不是近似。為讓四條斷言同時成立:

- **主鍵內嵌歸屬日**(`ORD-{tenant}-{YYYYMMDD}-{seq}`):遲到列的偵測走主鍵,不走日期欄——日期欄可能被缺值/漂移注入命中。
- **缺值池排除主鍵**:兩個以上空主鍵會互相碰撞,打破「總列數 − 相異主鍵數」斷言,也污染 dbt `unique` 的語意。分母仍照任務卡 = required 欄位數 × 基底列數。
- **注入目標互斥**:漂移避開已缺值的儲存格;重複列只複製未被注入且非遲到的列。
- **同 seed → byte-identical**:T1.4 的 idempotency 斷言(中途 kill 重跑結果一致)前提是輸入逐 byte 相同,否則差異無法歸因。

## 下游對口(每類髒資料由誰抓,T2.4 驗收依據)

| 髒資料 | 分母 | 抓它的環節 |
|---|---|---|
| 缺值(required 欄位變空字串) | required 欄位數 × 基底列數 | dbt `not_null` |
| 重複列(含主鍵) | 基底列數 | dbt `unique` |
| 欄位值漂移(decimal/datetime) | (decimal+datetime 欄位數) × 基底列數 | 自訂 test(注意:藍本 checker 視 `2024年3月14日` 等為合法,T2.4 需比藍本嚴的解析) |
| 遲到(整列延後到較晚的檔案日) | 基底列數 | T1.5 backfill |

本表用詞沿用 CONTEXT.md「漂移」與「日期」詞條的定義。

缺值實際的注入對象比表格寫的多一減一加:**主鍵不注入**(理由見上節),**訂單表的 `客戶編號` 額外納入**——它不是 required,但 2026-08-13 裁示把它加進來,為未來的孤兒鍵驗證留伏筆。除此之外只打 required 欄位,因為 nullable 欄位空著是合法值,沒有 test 會(也不該)抓它。注入筆數的分母不受這一減一加影響,仍照任務卡 = required 欄位數 × 基底列數。
